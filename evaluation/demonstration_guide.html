1. Executive Summary & Research Contribution

✔ The Core Problem Solved
Traditional Kubernetes schedulers and the Horizontal Pod Autoscaler (HPA) are strictly reactive. They trigger scaling only after worker nodes cross high CPU/memory utilization thresholds (e.g., 80%). Because spinning up containerized pods, scheduling, pulling images, and starting runtimes takes 30 to 90 seconds, sudden traffic surges cause severe cold-start latency spikes, SLO violations (>500ms), and service degradation.

1.1 Proposed Proactive Scheduling Architecture

This project proposes an end-to-end autonomous proactive scheduling framework that eliminates reactive cold-start penalties by predicting workload intensity 5 minutes ahead and preemptively binding pods to the optimal candidate node:

  1. Module 1 (Real Telemetry Collection): Direct PromQL scraper capturing CPU, memory, network I/O, and HTTP request rates from Kubernetes worker nodes.
  2. Module 2 (Preprocessing & Sequence Building): Chronological temporal split, robust MinMax scaling, lag feature generation (1-step, 2-step, 3-step lags, rolling window statistics), and 12-step lookback sequence tensors.
  3. Module 3 (LSTM-XGBoost Weighted Ensemble): Combines the long-term temporal pattern extraction of an LSTM Recurrent Neural Network with the sharp non-linear gradient-boosted decision trees of XGBoost via convex weighted fusion (\(R^2 = 0.9816\), lowest MSE/MAE).
  4. Module 4 (Multi-Objective Node Ranking Engine): Evaluates candidate nodes across four weighted dimensions: Predicted CPU Headroom, Predicted Memory Headroom, Network RTT Latency, and Cluster Load Variance.
  5. Module 5 (Kubernetes Pod Scheduler & Binding): Intercepts unscheduled pods matching schedulerName: proactive-scheduler and dispatches genuine Kubernetes API binding requests (POST /api/v1/namespaces/{ns}/pods/{name}/binding).
  6. Module 6 (Telemetry & Grafana Monitoring): Real-time Prometheus metrics exporter and custom 14-panel Grafana cluster dashboard.

2.1 Multi-Objective Mathematical Ranking Formulation

When a pod needs scheduling, the candidate nodes are filtered for hard constraints (Ready condition, schedulable, resource capacity). Surviving nodes are scored using the objective function:

\[S_i = w_{cpu}\left(1 - \hat{u}_i^{cpu} ight) + w_{mem}\left(1 - \hat{u}_i^{mem} ight) + w_{lat}\left(1 - rac{L_i}{SLO} ight) + w_{bal}\left(1 - B_i ight)\]

Where \(\hat{u}_i^{cpu}\) and \(\hat{u}_i^{mem}\) are the predicted future resource utilizations, \(L_i\) is measured network latency against the 500ms SLO threshold, and \(B_i = |\hat{u}_i^{cpu} - ar{u}_{cluster}^{cpu}|\) is the cluster variance penalty.

4. Anticipated Judge Questions & Bulletproof Defense

Q1: Why did you use an ensemble of LSTM and XGBoost instead of just using LSTM?

Answer: LSTMs are recurrent neural networks with gated memory cells that excel at capturing non-linear cyclic temporal dependencies and long-term diurnal seasonality. However, LSTMs can experience lag during sudden, sharp gradient shifts and have high training overhead. Conversely, XGBoost (Extreme Gradient Boosting) is an ensemble of decision trees that excels at rapid split decisions and non-linear feature interactions without memory overhead. By combining them via convex weighted fusion (\(w_1 \cdot ext{LSTM} + w_2 \cdot ext{XGBoost}\)), our ensemble achieves the lowest MSE (0.0018) and the highest \(R^2\) score (0.9816), compensating for each model's individual weaknesses.

Q2: How does your proactive scheduler bypass the default Kubernetes scheduler?

Answer: When a Kubernetes Deployment creates pods, the Pod specification includes schedulerName: proactive-scheduler. The default Kubernetes scheduler ignores any pod whose schedulerName does not match default-scheduler. Our custom scheduler controller monitors the Kubernetes API for pods matching our scheduler name that have spec.nodeName == "". Once candidate nodes are ranked using our multi-objective score, our controller issues a Kubernetes API binding sub-resource call (POST /api/v1/namespaces/{ns}/pods/{pod-name}/binding), atomically setting the node name and placing the pod.

Q3: What happens if the machine learning model makes an incorrect prediction?

Answer: Our architecture incorporates safety fallbacks at two levels:
1. Hard Constraint Filtering: Prior to scoring, nodes must pass hard Kubernetes filters (Ready status, unschedulable flag, and allocatable capacity checks). An over-predicted or under-predicted score can never place a pod on an overloaded or failed node.
2. Composite Balance Penalty: The balance term \(w_{bal}(1 - B_i)\) penalizes any single node from diverging significantly from the cluster mean utilization, preventing hot-spotting even under prediction noise.

Q4: Why does Reactive HPA suffer from high latency and SLO violations?

Answer: Reactive HPA calculates desired replicas as \(\lceil ext{current} imes ( ext{currentUtilization} / ext{targetUtilization}) ceil\). It relies on delayed metrics scraping (default Prometheus scrape interval 15s to 30s) and requires pods to cross the threshold first. Once triggered, container creation, container image pulling, runtime initialization, and readiness probes introduce a 30 to 90 second delay. During sudden traffic spikes, all incoming requests queue up against the unscaled instances, pushing response latency over 700ms and violating our 500ms SLO limit.

Q5: How does this scale to a 1,000-node cluster in production?

Answer: In a large-scale cluster:
1. Inference runs asynchronously in background polling threads decoupled from the scheduling loop.
2. The node ranking engine operates in \(O(N \log N)\) time where \(N\) is candidate nodes, and can use node filtering predicates (like Kubernetes node affinity and zone topology) to evaluate only surviving candidates.
3. We also provide a compiled Go Scheduler Plugin compatible with the native Kubernetes Scheduling Framework (PreFilter, Filter, Score, Bind extension points), running with sub-millisecond execution overhead.
